Halyard is a Redis-compatible database written from scratch in Go. Every write is replicated with Raft and acknowledged only once a majority has it on disk — so a node can crash at any moment and no confirmed write disappears.

        Features
        
A real database, not a wrapper.

        
Protocol, storage, persistence and consensus — all implemented here, with no external dependencies.

      

      

        

          
Raft consensus

          
Leader election with PreVote and CheckQuorum, log replication, snapshots, membership changes and
            leadership transfer. Failover in under half a second.

        

        

          
Linearizable reads

          
Reads go through ReadIndex: the leader confirms its authority with a quorum before answering, so a
            deposed leader can never serve stale data.

        

        

          
Sharding

          
16,384 hash slots across multiple Raft groups, Redis Cluster–style MOVED/ASK
            redirects, and live slot migration under load.

        

        

          
Durable storage

          
Checksummed append-only file with group commit, copy-on-write snapshots and crash-safe log rotation.
            Torn writes are detected and repaired on restart.

        

        

          
Redis data types

          
Strings, lists, hashes, sets and sorted sets on a hand-written skiplist, with TTLs and atomic
            MULTI/EXEC transactions.

        

        

          
Production basics

          
TLS, ACL users with roles, Prometheus metrics, INFO, config files, Docker images and a
            fault-injection API for demos.

        

      

    


    

      

        Correctness
        
Tested the way distributed systems fail.

        
Unit tests can't find consensus bugs. Halyard is checked against crashes, partitions and real Redis.

      

      

        

          2,000+
          
Deterministic simulation

          
Whole clusters run in one process on a virtual clock, with dropped, duplicated and reordered messages,
            partitions, crashes mid-fsync and log compaction. Every seed is reproducible. It found two real Raft bugs
            before they shipped.

        

        

          0 lost
          
Linearizability under faults

          
A Jepsen-style harness kills and partitions a real TCP cluster while clients read and write, then checks
            the full history for linearizability. Disabling ReadIndex makes the same harness fail — as it should.

        

        

          400k
          
Differential testing

          
Random command streams are sent to Halyard and to Redis 7; every reply must match byte for byte. The
            process even surfaced an index-truncation bug in Redis itself.

        Get started
        
Running in a minute.

      

      

        

          
          
          
        


# three nodes, each with its own disk; any node accepts clients
docker compose -f deploy/docker-compose.cluster.yml up -d --build
redis-cli -c -p 6381 SET hello world
redis-cli -p 6381 INFO replication


# one node with an append-only file, fsync every second
go run ./cmd/halyard -addr :6379 -appendfsync everysec
redis-cli SET hello world


# 3 Raft groups own the 16,384 slots; leaders are spread across nodes
halyard -id 1 -shards 3 -cluster 1=h1:7000/h1:6379,2=h2:7000/h2:6379,3=h3:7000/h3:6379
redis-cli -c -h h1 CLUSTER SLOTS
redis-cli -c -h h1 CLUSTER MIGRATE 5000 2   # live slot migration

      

    


    

      
FAQ
Questions engineers ask.

      

        
Is it a drop-in replacement for Redis?
For the supported subset — strings, lists, hashes, sets, sorted sets, TTLs, transactions, cluster redirects — yes: unmodified clients work. Lua, Pub/Sub, streams and RESP3 are not implemented.

        
What happens when the leader crashes?
Followers stop receiving heartbeats, a randomized election timeout fires, and a new leader is elected by majority vote — about 400 ms with test timeouts, ~1.3 s with defaults. Only writes that never reached a majority can be lost, and those were never acknowledged.

        
Are reads consistent?
Yes. Reads use ReadIndex: the leader confirms with a quorum that it is still leader before answering, so reads are linearizable even during partitions.

        
How fast is it compared to Redis?
83–100% of Redis 7 throughput on pipelined benchmarks on the same machine. Tail latency under heavy write contention is higher — see docs/benchmarks.md.

        
How do you know it's correct?
A deterministic simulator runs thousands of chaos seeds per test run, a Jepsen-style checker validates real cluster histories, and differential tests compare every reply with Redis 7.
